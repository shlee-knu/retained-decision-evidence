# SQLite retained-value migration: design fixed before execution

Recorded 2026-10-08, before implementing or preparing this new experiment. The machine-readable protocol is `configs/third_migration_protocol.json`. Prior code, artifacts and database snapshots remain unchanged. This is a local integration experiment on reconstructed public-data receipts, not a production cache or evidence of business error.

The practical job is to generate a replacement verdict receipt for each of 50,931 existing cases after selecting a target catalog. Case IDs and repeated activity projections are already available as the same common base input used in the preceding database experiment. The source is the preserved normalized SQLite database containing all 251,734 cases. A separate new SQLite table stores canonical JSON of each prior partial-observation receipt. Both databases are opened read-only during verification and measurement.

Four targets are fixed: identity baseline; the original strict Consignment catalog; the supplied globally equivalent catalog with a redundant transitive edge; and the supplied catalog requiring invoice under Consignment, which can change full labels. The old and new completion domains are Cartesian v1. We do not add guarantee-withdrawal timing or an expanded collection of favorable edits.

Three methods perform the same replacement-verdict task:

1. **Generic receipt:** fetch and decode the old receipt, bind it to the requested case and immutable snapshot, run the unchanged exact receipt recovery, and obtain missing P/T values through the real source accessor. It retains its additional old-certificate validation and migration diagnostics.
2. **Ordinary cache recomputation:** first test whether the common visible base already determines the new verdict, skipping the receipt entirely when it does. Otherwise fetch the old receipt and apply the same case, catalog, domain and snapshot checks. Recompute the new predicate with ordinary guards, reusing retained values and fetching missing fields as needed. Do not force this baseline to validate old-verdict sufficiency, preserve unneeded old values, or produce exact migration statuses that its new-verdict task does not need.
3. **Fresh guarded join:** inspect only the common base and new rules. Reject structurally impossible cases without metadata; otherwise retrieve both source blocks in one joined statement and evaluate the actual profile. This method pays no old-receipt lookup or parsing cost. Giving it this stronger interface avoids making fresh recomputation unnecessarily expensive.

All methods serialize a replacement receipt with the same schema, new catalog/domain binding, immutable snapshot, case identifier, repeated activities, new Boolean verdict and their actual observed values. Observed sets can differ: retained data may include redundant fields, whereas a fresh structural rejection may require none. Every output must be sufficient for its recorded new verdict. Encoding and output byte/digest accounting are measured; durable output writes are deliberately excluded. This is a receipt-generation component, not an atomic cache-migration transaction.

The new adapter must require `receipt_id == requested case_id`, exact agreement between the receipt activities and common base, matching snapshot and old catalog/domain, and supported observed fields. Metadata queries use only that same requested case ID. These checks catch misplaced or mismatched records; they cannot authenticate deliberately forged matching records or detect changes in unread source values. The immutable source assumption is fixed and checked by file hashes. Missing receipt/source rows and swapped receipts have explicit regression tests, including cases where an unneeded source row must remain unread.

Generic setup constructs its universal state and completion-fiber tables from empty semantic caches for each measured job. Setup wall/CPU and per-case migration wall/CPU are reported separately and summed into the batch total. The other methods' lightweight rule setup is measured on the same boundary. Within-batch reuse of catalog-level semantic tables is permitted; decoded per-case metadata and decisions never carry to another case or repetition. Connection setup and destruction/reset of the previous job's caches are environmental preparation outside the next batch timer.

Generic revalidation performs one actual receipt-table SELECT per case for its old-receipt assurance; ordinary recomputation performs it only after its base guard fails to decide. Receipt SQL/rows/bytes are distinct from source SQL/returned P/T values/bytes; their sum gives the actual statement count. Source and receipt JSON decodes, retained/new observations and replacement output bytes are counted. SQL traces independently check statements during untimed correctness verification and are disabled for timing. Receipt-store construction time, stored bytes, relation digest and input decoding/serialization are reported separately. Original source DB construction is reused historical preparation; the original raw-XES projection cost is not newly measured.

The primary matrix is one normalized layout × four catalogs × three methods. Two complete warmup rounds precede seven complete measured rounds, giving 108 full-cohort jobs. Method and case orders are fixed-seed randomized. CPU 23 is used if allowed; the run waits for a coordinated quiet slot. Page and statement caches follow the previous warm local SQLite setting; there is no artificial sleep, padding, network, concurrent writer or cold-cache claim. Report CPU and wall distributions and paired differences for every method and target, including negative or near-null outcomes.

The strict generic recovery expectation is already known: 33,489 new P values and 1,471,664 source JSON bytes, with no new T values. Cached methods also incur receipt-store costs that the previous logical replay did not measure. The old 52,855 block reads/6,705,042 bytes are sunk historical acquisition, never charged as new SQL work or subtracted from it. The prior fresh strict guarded join required 41,597 source statements and 8,152,814 bytes. These are known reconciliation checks. New receipt-store costs, replacement output sizes and all new setup/migration times are unknown at design freeze and may favor fresh recomputation or the ordinary cache baseline.

The meaningful comparisons are ordinary cache versus fresh guarded join for this migration interface, and generic versus ordinary cache for the extra exact revalidation service. They do not establish a novel faster optimizer. A generic disadvantage is a useful deployment boundary; a caching advantage would remain conditional on the existing retained values and exclude their initial collection/storage cost. Storage amortization, durable persistence, remote service latency and live-source freshness remain unmeasured.

Implementation will use only new `scripts/benchmark_receipt_migration.py`, `tests/test_receipt_migration.py`, and `results/third/sqlite_migration/` outputs. Preparation records source/config/code hashes and refuses overwrite. Native verification checks all 12 method/target combinations against an independent raw predicate reference and checks output sufficiency. Idempotence applies to the new replacement receipt under an unchanged target and snapshot: it needs no new source values, but receipt access and computation are not free. Timing begins only after correctness checks and explicit coordination; no result-dependent matrix or round selection is permitted.

For reproduction, generated SQLite databases remain outside the review archive. The canonical default requires the exact preserved normalized database file hash. An explicit preparation `--source-db` override may use a regenerated database after its entire 251,734-row keyed P/T relation matches the prior pinned length-framed row digest. This accommodates legitimate SQLite binary-layout differences across versions without accepting different data. The new execution records that database's actual file hash and requires it to remain unchanged from preparation through timing. Receipt-store binaries are newly generated and recorded for each run. Rebuilding the original normalized layout uses the earlier database-preparation command with a fresh output directory; the override then points to its `normalized.sqlite3`.
